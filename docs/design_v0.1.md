# 궤도 정비소 — 설계방향 검토안 v0.1

작성일: 2026-09-24  
가제: 궤도 정비소 / Orbital Workshop  
전제: 1인 또는 소규모 개발, 싱글플레이, PC 키보드·마우스 우선. 플랫폼·팀 규모는 아직 확정되지 않았으며 아래 범위와 수치는 시제품 검증을 위한 제안이다.

## 1. 추천하는 게임의 중심

**작은 궤도 정비소의 작업선을 몰고 고장 난 위성을 찾아가, 움직임을 안정시키고 고장 원인을 찾아 고친 뒤, 다시 살아나는 서비스를 확인하는 3D 작업 어드벤처.**

플레이어가 기억해야 할 세 장면은 다음과 같다.

1. 회전하는 위성에 조심스럽게 다가가 포획 장치를 걸었을 때의 손맛.
2. 관찰한 증상과 측정값을 연결해 고장의 원인을 알아냈을 때의 만족감.
3. 패널이 펼쳐지고 안테나가 돌아가며 고객의 통신이 다시 들릴 때의 보상.

‘내가 고쳐서 누군가 다시 연결됐다’는 감정을 중심에 둔다. 기술적 깊이는 관찰과 판단에서 나오고, 조작은 처음 보는 사람도 이해할 수 있게 만든다.

## 2. 세 가지 설계 방향 비교

| 방향 | 주된 재미 | 장점 | 설계상 어려움 | 채택 방식 |
|---|---|---|---|---|
| 정밀 작업 시뮬레이션 | 자세 맞추기, 포획, 로봇팔 운용 | 3D·무중력의 특징이 선명함 | 조종 난도와 반복작업 피로 | 접근·포획의 핵심 조작으로 반영 |
| 서비스 복구 어드벤처 | 진단, 수리, 복구 결과와 사람들의 이야기 | 작업에 목적이 생기고 임무를 다양하게 만들기 좋음 | 고장 원인과 단서를 세심하게 설계해야 함 | **게임 전체의 중심으로 채택** |
| 궤도 출장·정비소 경영 | 장비 선택, 견인, 수주와 확장 | 우주 배송 구상과 연결하기 좋음 | 이동·경제·작업 시스템이 동시에 커질 수 있음 | 핵심 작업 검증 후 얕은 성장 요소부터 추가 |

초기에는 서비스 복구에 필요한 조종과 정비를 완성한다. 정비소는 귀환 장소이자 장비 선택 화면으로 시작하고, 운영 규모는 검증 결과에 맞춰 확장한다.

## 3. 세계관과 플레이어의 위치

정비용 결합부와 교체식 외장 장비가 일부 위성에 보급된 근미래를 가정한다. 이는 게임의 창작 설정이며, 현재의 모든 위성이 궤도상 정비를 전제로 설계되었다는 뜻은 아니다.

플레이어는 지구 저궤도의 소규모 정비소에서 작업선을 운용한다. 주변에는 기상·통신·관측 위성과 작은 연구 정거장이 있다. 고객은 지상 관측팀, 원격지 통신 운영자, 연구원, 우주 화물선 등으로 구성한다.

초기 무대는 같은 궤도대의 제한된 작업 구역이다. 장거리 궤도 이동은 지도상의 임무 선택과 짧은 전환으로 압축하고, 직접 조종은 대상 근처에서 시작한다. 화면의 지구와 먼 시설은 배경 연출이고, 실제 작업 공간은 위성 주변의 작은 구역이다.

톤은 차분하고 생활감 있는 산업 SF다. 반복해서 찾아오는 고객과 낡은 정비소의 변화가 서사를 만든다. 보통 의뢰는 여유롭게 진행하고, 긴급 의뢰를 선택했을 때 제한시간과 추가 조건이 붙는다.

## 4. 플레이 흐름과 중요한 선택

| 단계 | 플레이어가 하는 일 | 생기는 판단 | 즉시 보여줄 반응 |
|---|---|---|---|
| 의뢰·준비 | 증상을 읽고 도구·예비품 선택 | 측정 장비를 더 챙길지, 교체품을 실을지 | 작업선 적재함의 변화 |
| 접근·관찰 | 위성 주위를 돌며 상태 확인 | 포획점과 돌출 구조물을 피해 어느 쪽으로 접근할지 | 상대속도 표시, 접근 경고, 작업등 |
| 포획·안정화 | 속도와 방향을 맞추고 결합 | 기다릴지, 자세를 바꿀지, 다시 접근할지 | 결합 장치 잠금, 잔여 회전 감소 |
| 진단 | 외관·전력·온도·응답을 관찰 | 같은 증상을 만드는 여러 원인 중 무엇인지 | 측정값과 물리적 단서 |
| 정비 | 전원을 분리하고 부품·연결부 작업 | 현장 수리, 예비품 교체, 견인 중 선택 | 부품 이동, 연결 상태, 작동 시험 |
| 검증 | 전력·자세·통신 동작 확인 | 고장이 해결됐는지, 남은 문제가 있는지 | 패널 전개, 안테나 지향, 신호 복구 |
| 귀환·성장 | 보수·장비 변경·다음 의뢰 선택 | 다음에 어떤 작업을 할지 | 정비소 장비와 고객 서비스 변화 |

모든 임무가 모든 선택지를 제공할 필요는 없다. 초반은 정해진 도구로 한 고장을 해결하고, 이후 현장 수리와 견인의 장단점을 비교하게 한다.

## 5. 조종과 포획: 손맛을 만드는 방법

### 기본 시점

작업선 뒤쪽의 3인칭 시점을 기본으로 한다. 선체, 대상 위성, 접근 방향을 함께 볼 수 있어 거리와 회전 상태를 읽기 쉽다. 정비 중에는 로봇팔 끝의 작업 카메라로 부드럽게 전환한다. 자유로운 카메라 회전은 제공하되 기본 화면의 수평 안정화와 화면 흔들림 조절을 넣는다.

### 조작의 원칙

- 이동·상호작용·도구 사용을 상황에 맞게 연결한다.
- 초기에는 자세 안정화를 기본으로 제공하고, 수동 롤 조작은 선택 기능으로 둔다.
- 제동 버튼은 선택한 대상에 대한 상대속도를 줄이는 보조 기능으로 만든다.
- 관성 이동은 유지하고, 추진·제동·자세 보정 때 추진제 사용을 보여준다.
- 자동 보조는 플레이어가 지정한 목표를 따라 제한된 속도로 작동한다. 성공 자체를 대신해주는 즉시 정렬은 피한다.

### 포획 성공의 조건

포획은 조준점이 겹쳤다는 이유만으로 완료하지 않는다. 포획점까지의 거리, 결합부 방향, 접촉점의 상대속도, 회전 차이가 허용 범위에 들어와야 결합할 수 있게 한다. 초기에는 허용 범위를 넓게 두고 설명을 시각적으로 제공한다.

회전하는 위성에는 움직이는 포획점이 있다. 회전축과 가까운 곳으로 이동하거나 다음 접근 기회를 기다리는 선택이 가능해야 한다. 강한 회전 표적은 후반 임무에 배치하고, 초반 대상은 자세가 유지되거나 매우 느리게 회전하도록 만든다.

도킹 후 안정화는 작업선의 자세제어가 수행하는 것으로 표현한다. 모델을 단순화하더라도 화면에서 회전이 갑자기 사라지지 않도록 한다.

실제 비협조 표적 포획도 접근·상대운동·로봇 포획이 핵심 과제다. ESA의 2026년 ClearSpace-1 발표는 전용 포획 인터페이스가 없는 회전 표적에 대한 접근·포획과 파편 발생 억제를 다룬다. 이는 게임 소재의 근거이고, 본 게임의 조작·허용 범위는 별도로 정한다.[3]

## 6. 진단과 정비: 왜 이 행동이 필요한지 알 수 있게

스캐너는 고장의 정답을 바로 표시하기보다 관찰 가능한 정보를 제공한다. ‘출력 낮음’, ‘명령 응답 없음’, ‘해당 부분 온도 높음’ 같은 정보와 3D 외관을 연결해 판단하게 한다. 확인한 정보는 간단한 작업 기록에 남겨 반복 측정의 부담을 줄인다.

| 증상 | 가능한 원인 예시 | 구별하는 단서 | 정비 행동 | 확인할 결과 |
|---|---|---|---|---|
| 전력 공급 부족 | 태양전지판 전개부 고착 | 한쪽 패널이 접힌 외관, 전개 명령 후 위치 변화 없음 | 전개부 안정화, 래치 해제 | 패널 전개와 발전 상태 회복 |
| 통신 불가 | 안테나 구동부 이상 또는 통신장비 전원 문제 | 전원 상태와 지향 명령 응답을 비교 | 구동 장치 교체 또는 전원 연결 복구 | 시험 신호 수신 |
| 자세 유지 실패 | 게임 내 교체식 자세제어 모듈 고장 | 명령은 접수되지만 회전이 줄지 않음 | 포획·안정화 후 모듈 교체 | 방출 후 자세 유지 |
| 작업 중 성능 저하 | 게임 내 열제어 장치 이상 | 부하를 올렸을 때 온도와 성능의 동반 변화 | 열제어 모듈 정비, 부하 조절 | 시험 부하에서 상태 유지 |

표는 단순화한 게임용 고장 모델이다. 실제 장비의 고장 진단 절차나 운용 기준으로 사용하지 않는다.

첫 구현에는 한 개의 고장과 명확한 단서만 둔다. 이후 같은 증상에 두 원인이 가능한 의뢰를 추가한다. 무작위 고장은 원인·단서·도구·정비 행동이 서로 맞는 조합 안에서만 생성한다.

정비 행동은 ‘누르기’의 반복을 줄이고 공간적 판단을 포함한다. 반대편으로 돌아가야 보이는 연결부, 구조물을 피해 넣어야 하는 교체품, 먼저 고정해야 움직이지 않는 부품 등을 사용한다. 자유로운 절단 대신 정해진 결합부에서 분리·재결합하는 구조를 적용한다.

## 7. 첫 10분 임무: 다시 펼쳐지는 날개

### 임무 설정

기상위성의 태양전지판 한쪽이 전개되지 않았다. 위성은 예비 전력과 자세제어를 유지하고 있으며, 당장은 안정적이다. 원인은 정비 가능한 외장 전개부의 래치 고착 하나다. 첫 임무에는 시간 제한을 두지 않는다.

아래 시간은 플레이 리듬의 목표이며 실제 플레이 결과에 따라 조정한다.

| 목표 시간 | 장면·행동 | 배우는 것 |
|---|---|---|
| 0~1분 | 짧은 의뢰 수신. 장비는 미리 탑재된 상태로 시작 | 무엇을 복구해야 하는지 |
| 1~3분 | 위성 주변을 돌아보며 접힌 패널과 포획점 확인 | 이동·감속·거리 읽기 |
| 3~5분 | 결합부에 접근해 고정. 작업 카메라 전환 | 자세 맞추기와 포획 |
| 5~7분 | 전개 명령과 외관을 비교해 래치 문제 확인. 구동 전원 분리와 전개부 고정 | 증거를 보고 원인 좁히기 |
| 7~9분 | 래치를 해제하고 정해진 순서에 따라 전개 시험 | 도구 사용과 순서의 의미 |
| 9~10분 | 발전·통신 시험. 고객의 기상 화면과 무전이 회복 | 작업의 결과와 다음 의뢰 기대 |

마무리는 보상 팝업만으로 끝내지 않는다. 패널이 펼쳐지고, 정상 작동 표시가 켜지고, 지상의 관측 데이터가 갱신되는 변화를 보여준다. 고객의 짧은 감사 무전이 복구 장면과 연결된다.

첫 임무에서 부딪히거나 접근에 실패하면 가까운 접근 지점에서 다시 시도할 수 있게 한다. 이미 알아낸 진단 정보는 유지한다. 실패 후 복귀가 조종 연습보다 오래 걸리는 구조를 피한다.

## 8. 임무를 늘리는 순서

| 순서 | 의뢰 | 새로 추가되는 재미 | 재사용하는 요소 |
|---|---|---|---|
| 1 | 접힌 태양전지판 | 관찰·접근·포획·단일 수리 | 기본 작업선과 위성 |
| 2 | 신호가 약한 통신위성 | 지향 문제와 전원 문제 구별 | 스캔·전원·결합부 |
| 3 | 천천히 회전하는 위성 | 움직이는 포획점 접근과 안정화 | 동일 포획 장치 |
| 4 | 현장 수리로 끝내기 어려운 고장 | 예비품 선택과 견인 판단 | 교체식 모듈·귀환 지점 |
| 5 | 서로 연관된 두 장비의 이상 | 원인을 해결한 뒤 재시험 | 기존 고장과 시험 절차 |

임무 다양성은 처음부터 많은 위성을 만드는 것보다 접근 자세, 단서, 고장 위치, 사용 가능한 도구의 조합에서 만든다. 위성 형상 3종과 임무 5개는 알파의 목표이며, 그 전에 위성 1종·고장 1개로 재미를 확인한다.

지구 그림자 진입에 따른 배터리 제약, 느리게 움직이는 큰 구조물, 낡은 포획 인터페이스는 이후의 작업 조건으로 추가한다. 그림자 진입이 즉시 실패를 뜻하지 않도록 잔여 전력과 복구 방법을 제공한다.

## 9. 성장과 경제

성장은 새로운 행동을 가능하게 해야 한다.

| 장비·시설 | 열리는 선택 |
|---|---|
| 더 정밀한 추진기 | 작은 틈과 좁은 결합부에 접근 |
| 긴 작업 팔 | 돌출 구조물 뒤의 부품에 도달 |
| 개선된 스캐너 | 외관만으로 구분하기 어려운 원인 진단 |
| 추가 적재함 | 교체품을 챙겨 현장 수리 선택 |
| 견인 결합 장치 | 복잡한 위성을 정비소로 가져와 작업 |

초기 경제는 의뢰 보상, 사용 부품 비용, 장비 구입 정도로 구성한다. 무사 복구, 원래 장비 보존, 추진제 사용은 선택적인 평가 항목으로 둔다. 최소 성공만 해도 다음 기본 임무를 진행할 수 있게 설계한다.

복구가 끝난 위성은 서비스 지도에서 정상 상태로 남는다. 새 의뢰는 새 고객과 새로운 작업 조건으로 확장한다. 진행을 유지하려고 같은 위성을 계속 고장 내기보다 정비소의 서비스 영역이 커지는 모습을 보여준다.

## 10. 화면·미술·소리

- 미술: 형태가 분명한 저폴리곤 또는 간결한 사실적 모델. 무광 외장, 노란 작업 팔, 금속 결합부, 푸른 지구를 주요 요소로 사용한다.
- 기본 화면: 중앙은 작업 공간, 가장자리에는 상대속도·도구 상태·현재 목표만 표시한다.
- 작업 중: 필요한 측정값을 대상 옆에 표시하고, 화면 전체를 표와 수치로 덮지 않는다.
- 정보 표현: 색상과 함께 모양·문자를 사용한다. ‘정상/이상’은 색만으로 구분하지 않는다.
- 카메라: 자동 회전 강도, 흔들림, 수평 안정화를 조절할 수 있게 한다.
- 소리: 무전, 선내 기계음, 접촉 진동을 전달하는 효과음, 센서 알림으로 작업 상태를 표현한다.
- 정비소: 짧은 귀환 장면, 고객 사진·메시지, 추가된 공구와 적재함으로 생활감과 성장을 보여준다.

## 11. 개발 범위와 검증 관문

### 단계 A — 조종·포획 검증

구형 임시 모델, 작업선 1대, 대상 1개, 상대운동, 제동, 포획 조건, 재시도 기능을 만든다. 목표는 설명을 짧게 듣고 접근과 포획을 이해할 수 있는지 확인하는 것이다.

정지 표적과 저속 회전 표적을 차례로 시험한다. 포획이 답답하면 시각 안내, 제동 감도, 허용 범위를 조정한다. 다음 콘텐츠를 늘리기 전에 조종의 납득성과 카메라 편안함을 해결한다.

### 단계 B — 첫 임무 완주

위성 1종, 래치 고착 1개, 스캔·고정·정비 도구, 전개 시험, 복구 연출을 붙인다. 이 단계의 완성물은 앞의 10분 임무다. 도구는 하나의 작업 팔에서 기능을 전환하는 형태로 구현할 수 있다.

### 단계 C — 알파

위성 형상 3종, 임무 5개, 서로 구분되는 고장 3종, 정비소 메뉴, 소수의 장비 업그레이드, 저장·불러오기를 추가한다. 고장 3종은 기계적 고착, 연결 이상, 교체식 모듈 고장으로 제한하고, 이를 임무에 배치한다.

### 후속 후보

긴급 의뢰, 견인 작업의 확장, 구형 위성 어댑터, 우주 배송 연계, 정비소 증축, 협동 작업을 후보로 유지한다. 협동 플레이는 물리 동기화와 역할 분담의 별도 설계가 필요하므로 싱글플레이 검증 후 판단한다.

### 초기 관찰 지표

3~5명의 소규모 관찰에서 다음을 확인한다. 표본은 개선점을 찾기 위한 것이며 시장성을 증명하는 규모는 아니다.

- 도움을 요청하는 지점이 조종, 카메라, 포획 조건, 진단 중 어디인지.
- 플레이어가 위성이 왜 고장 났고 자신이 무엇을 고쳤는지 설명할 수 있는지.
- 재시도를 실패 원인을 배우는 과정으로 받아들이는지.
- 완료 장면에서 복구된 기능을 알아차리는지.
- 다른 고장을 가진 두 번째 위성도 고쳐보고 싶어 하는지와 그 이유.

시간과 성공률은 기록하되 수치 하나만으로 재미를 판정하지 않는다. 고장을 이해하지 못한다면 단서를 개선하고, 손은 바쁜데 판단이 없다면 의미 없는 클릭을 줄인다.

## 12. 구현 방향의 잠정안

### 엔진·플랫폼

본격적인 3D 게임 제작을 기준으로 Godot 4.x와 GDScript를 우선 검토한다. 엔진의 구체 버전은 구현을 시작할 때 고정한다. 기본 조작은 PC 키보드·마우스로 설계하고, 브라우저는 공유·시연 대상에 포함할 수 있다.

공식 문서 기준 Godot 4의 웹 출력은 WebAssembly와 WebGL 2.0이 필요하고 Compatibility 렌더러를 사용한다. GDScript를 선택하면 현재 웹 출력이 지원되지 않는 Godot 4 C# 경로를 피할 수 있다. 웹을 초기 목표에 포함하면 첫 포획 시제품부터 실제 대상 브라우저에서 성능과 입력·저장을 확인한다.[4]

웹 링크를 통한 가벼운 시제품 전달이 최우선으로 확정된다면 Three.js 기반 별도 시제품도 비교할 수 있다. 다만 게임을 오래 확장하는 목표에서는 장면 편집, 물리, 입력, 저장 작업을 함께 관리할 수 있는 개발 방식을 우선한다. Python은 임무 데이터 생성과 검증에 활용할 수 있다.

### 물리의 경계

- 근접 작업은 국소 상대 좌표에서 구현한다. 먼 지구와 공전은 시각적 배경으로 분리한다.
- 이 방식은 정밀 궤도 전파가 아닌 짧은 작업 구간의 게임용 근사다. 긴 자유비행과 궤도 기동으로 확장할 때는 별도의 모델이 필요하다.
- 활성 물리 대상은 작업선·대상 위성·현재 다루는 부품에 집중한다.
- 자유 물체의 임의 감쇠와 조종 보조를 구분하고, 보조 동작은 추진기 연출과 함께 보여준다.
- 포획 전후의 결합 상태와 상대운동 처리를 명확히 해 갑작스러운 이동이나 진동을 줄인다.
- 부품은 사전 정의한 결합부로 연결하며, 부품 분리와 기능 상태의 변경을 같은 사건으로 처리한다.

### 모듈 구분

| 모듈 | 책임 |
|---|---|
| 작업선 제어 | 입력·추력·보조 제동·카메라 |
| 포획·결합 | 접근 판정·결합 상태·안정화 |
| 위성 기능 | 전력·자세·통신의 단순화한 상태와 의존관계 |
| 고장·진단 | 원인·관찰 가능한 단서·검사 결과 |
| 정비 상호작용 | 전원 분리·결합 해제·교체·복구 |
| 임무 | 목표·조건·검증·재시도 지점 |
| 성장·저장 | 보상·장비·완료 의뢰·진행 상태 |

임무 성공은 단순히 ‘부품을 눌렀는지’가 아니라 관련 기능 상태와 시험 결과를 기준으로 판정한다. 고장 데이터에는 원인, 나타나는 증상, 검사 방법, 수리 행동, 검증 조건을 함께 넣어 불가능한 임무 조합을 막는다.

## 13. 먼저 확정할 것과 시제품으로 결정할 것

| 항목 | 현재 제안 | 결정 방법 |
|---|---|---|
| 핵심 정체성 | 서비스 복구를 하는 궤도 정비사 | 설계의 기준으로 사용 |
| 기본 시점 | 3인칭 접근·작업 카메라 정비 | 포획 시제품으로 편안함 확인 |
| 현실성 | 근접 운동과 고장 인과관계를 우선 | 이해도와 재미를 보며 조정 |
| 첫 임무 | 태양전지판 전개부 복구 | 위성 1종·고장 1개로 완주 검증 |
| 기본 분위기 | 차분한 작업과 고객의 생활 이야기 | 짧은 무전·복구 연출 반응 확인 |
| 경영 깊이 | 장비와 의뢰 선택 중심 | 반복 플레이가 성립한 뒤 확대 |
| 플랫폼 | PC 우선, 웹 시연 검토 | 사용자가 원하는 배포 방식과 초기 성능으로 확정 |

앞서 구상한 우주 배송 게임과는 같은 세계관을 공유할 수 있다. 배송선이 고장을 신고하거나 정비소가 예비품 배송을 요청하는 접점이 자연스럽다. 첫 단계에서는 궤도 정비소 자체의 한 임무를 완성한 뒤 두 프로젝트의 연결 수준을 정한다.

## 14. 참고자료와 설계에 반영한 범위

아래 자료는 실제 사례·도구의 근거다. 본 문서의 세계관, 조작, 임무, 진행 구조와 개발 범위는 이 프로젝트를 위한 설계 제안이다. 확인일은 2026-09-24다.

1. [Blackbird Interactive — Hardspace: Shipbreaker](https://www.blackbirdinteractive.com/shipbreaker)  
   도구를 이용한 우주선 해체·회수와 장비 성장을 참고했다. 이 프로젝트에서는 작업 행동에 따른 물리적 반응을 살피는 비교 사례로 활용한다.
2. [Shape Shop — Mars First Logistics, 공식 Steam 소개](https://store.steampowered.com/app/1532200/Mars_First_Logistics/)  
   직접 만든 로버로 화물을 운반하고, 작업 완료가 새로운 시설과 연결되는 구조를 참고했다. 본 프로젝트의 복구 후 서비스 변화는 이를 바탕으로 별도로 제안한 설계다.
3. [ESA Clean Space Days 2026 — ADRIOS ClearSpace-1](https://indico.esa.int/event/644/contributions/12346/)  
   비협조 회전 표적의 근접 접근·포획, 전용 인터페이스 부재, 파편 발생 억제라는 작업의 특성을 확인했다. 실제 임무의 목표는 표적 제거이며 이 문서의 위성 수리 설정과 구분한다.
4. [Godot Engine — Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)  
   웹 출력에 필요한 기술, 렌더러 및 언어 제약을 확인했다. 세부 지원 상태는 구현 버전을 확정할 때 다시 점검한다.
